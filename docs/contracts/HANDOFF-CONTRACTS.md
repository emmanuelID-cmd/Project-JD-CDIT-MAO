## 1. Contribution envelope (every agent output)

Every agent contribution extends `AgentContribution`. Models are frozen and reject unexpected fields, so a contribution cannot be changed after handoff.

| Field | Meaning |
| :--- | :--- |
| `contract_version` | `0.1.0-proposed`. Consumers reject other versions. |
| `contribution_id` | Deterministic ID (`KNW-…`, `TRB-…`, `DOC-…`). The same inputs give the same ID, so retries are idempotent. |
| `stage`, `agent`, `agent_version` | Who produced it. |
| `context` | `RunContext`: `run_id`, `case_id` (must match `SYN-…`), `case_version`, `policy_version`, `data_classification="synthetic"`. This is the join key. |
| `input_refs` | The upstream contributions consumed: ID, stage, contract version, and (proposed S-2) `content_digest`, the canonical SHA-256 of the exact contribution consumed. Provenance chain. |
| `created_at` | Timezone-aware timestamp (UTC proposed; see D-10). |
| `status` | `completed`, `abstained` (ran safely but declined to give guidance) or `blocked` (input or output failed validation). |
| `checkpoint` | PRD gate (`A2`–`A6`), `passed`, `reason_codes`. `status == completed` exactly when `passed`. |
| `claims` | Material claims, each labelled `verified` (needs sources), `inference` (needs a basis) or `unknown` (never high confidence). |
| `confidence`, `confidence_rationale` | Provisional band: `high` ≥ 0.85, `medium` 0.60–0.84, `low` < 0.60. Uncalibrated (D-08). |
| `unknowns` | Open questions carried forward. |
| `human_review_required` | Always `true`. The schema rejects `false`. |

`SourceRef` points at evidence without copying it: `kind` (`kb_section`, `kb_step`, `case_field`, `staff_entry`, `policy_rule`, `contribution`), `source_id`, `version`, `locator`. Citations are ASCII, for example `KB-NAV-001 v2.1 #s1/st2`.

## 2. Acceptance rules applied by Shawn's agents (receiving side)

Before using any upstream contribution, the Knowledge, Troubleshooting, and Documentation agents check that:

1. its `context` equals the current `RunContext`. A stale case, policy, or run version gives `context_mismatch`;
2. its `contribution_id` is in the coordinator's acknowledged set, otherwise `upstream_not_acknowledged`;
3. it is not `blocked`, and Triage is `completed`, otherwise `upstream_blocked`;
4. downstream contributions list the upstream IDs they were built from, with a content digest that matches the contribution received, otherwise `upstream_chain_mismatch`. The same ID with different content is a different input;
5. for a linked item, the item passes the eligibility gate (section 3a), every stage works on the same item, and stages after Knowledge wait for the Auditor.

**Proposed coordinator obligation (Manny's Lane):** pass each agent the set of contribution IDs the coordinator has acknowledged. Acknowledgment is recorded at the blackboard level, not inside the frozen contribution.

## 3. Connection points

| Handoff | Producer → consumer | Payload | Notes |
| :--- | :--- | :--- | :--- |
| Triage → Knowledge / Troubleshooting / Documentation | Manny → Shawn | `TriageHandoff` (*consumer-side proposal*) | Shawn reads `case_summary` (minimized; untrusted; used only as a retrieval query and for restricted-request patterns), `product_area`, `category`, `category_confidence`, `urgency`, `case_facts[]` (`field`, `value`, `verified`, `source`), `missing_facts[]`, and the optional `item_scope` (section 3a). Manny's Lane owns Triage and may propose different fields. |
| Knowledge → Troubleshooting | Shawn → Shawn | `KnowledgeResult` | `passages[]` carry verbatim approved text, steps, information items, and stop conditions, plus `relevance`, band, and source. Abstention carries `excluded_sources`, `conflicts`, and `injection_flags` (IDs only, no injected text). |
| Troubleshooting → Escalation / Documentation | Shawn → Manny / Shawn | `TroubleshootingResult` | `steps[]` (Tier 1 only, `suggested_not_performed`), `staff_only_procedures[]`, `stop_conditions[]` (`triggered` true or null), `information_needed[]`, `rejected[]`, `escalation_signals[]`. **Signals are inputs for the Escalation agent, not decisions.** |
| Escalation → Documentation | Manny → Shawn | `EscalationHandoff` (*consumer-side proposal*) | `must_escalate` (true, false or null), `triggers[]`, `recommendation` (`escalate_l2`, `escalate_support_lead`, `human_review`, `no_escalation_proposed`), `reason`. Required: Documentation suppresses the draft if it is missing. |
| Documentation → Coordinator / human review | Shawn → Manny | `DocumentationResult` | Exactly one of `draft` (`DraftNote` with banner, labelled sections, `rendered_text`) or `manual_fallback` (reason codes + instructions). `privacy_findings` give category and location only. Nothing is saved or sent. |

`RecordedAction` (coordinator → Documentation) carries staff-entered actions with a `staff_entry` source. Only `verified` actions appear as performed.

## 3a. Linked-item scope (proposed S-1, 2026-11-06)

When one case message holds several distinct requests, Manny's Triage splits it into linked items. Each item can then travel as its own `TriageHandoff`, with `case_summary` set to the item text only and `item_scope` set. `item_scope = None` keeps the single-case path unchanged.

**`TriageItemScope` fields**

| Field | Rule |
| :--- | :--- |
| `identity` (`LinkedItemRef`) | `scope_contract_version` (`triage-item-scope-0.2-proposed` for new scopes; legacy `triage-item-scope-0.1-proposed` keeps the S-1 rules); `item_id`; `item_index` and `item_count` (1 to 8); `parent_source` (`case_field`, this case and case version, locator `message`); `parent_digest` (SHA-256 of the parent message); `source_start` and `source_end` (codepoint span). |
| `item_id` | `stable_id("ITM", run_id, case_version, parent_digest, item_index, source_start, source_end)`, approved by Manny (Q-C). It is run-scoped: a new run, case version, or segmentation may give a new ID. |
| `segmentation` | `candidate_boundary` or `ambiguous_parent`. An ambiguous parent must abstain and has no category. |
| `depends_on` | Other item indexes. Each must exist, must not be the item itself, and must not repeat. |
| `item_status` | `proposal_for_human_review` exactly when the handoff `status` is `completed`. |
| `category_label`, `category_basis`, `category_sources` | An `inference` needs a basis and sources and matches a non-empty `category`. An `unknown` has neither and no `category`. Case sources must be this case version; policy sources must be this policy version. **Exception (0.2 only):** a `policy_rule` source named `SYN-TICKET-CATEGORY-TAXONOMY` must instead be a content-addressed reference: locator `category_sha256:<64 lowercase hex>`, version `sha256-<first 16 hex>` (`item_claim_taxonomy_source_mismatch`). This mirrors Triage's own rule; trust in the taxonomy content stays with Triage's pinned loader. |
| `category_evidence_span` | Optional; must lie inside the item span. |
| `auditor_review` | `pending` or `band_and_route_determined`. `band_and_route_determined` requires an urgency other than `unknown`. |
| `attention_ref`, `parent_attention_flagged` | A reference to this item's attention flag, never its text (Q-B). A flagged item implies the parent summary flag. |
| `attention_check` (0.2 only, optional) | `potential_attention` exactly when `attention_ref` is set; `no_configured_match` (the literal check ran on this item, nothing matched; never a risk assessment); `check_not_run` (requires no parent flag); `None` means Triage did not say. A 0.1 scope must leave it unset. Rejection reasons: `attention_check_ref_mismatch`, `attention_check_not_run_but_parent_flagged`, `attention_check_requires_scope_0_2`. It becomes required for 0.2 once Manny's connector always fills it (S-1.1 Q5). |

Development example references are not part of the handoff; the schema rejects unexpected fields.

**Receiver rules (Shawn's agents)**

- **Knowledge** retrieves for an item that is `candidate_boundary`, has no dependencies, has an inferred category, and is a proposal for human review. Unknown urgency is allowed: retrieval is read-only and may run while the Auditor reviews urgency (Q-A). Otherwise it returns `blocked` (`upstream_blocked`, `upstream_chain_mismatch`, or `context_mismatch`) without retrieving. The query is the item text only. Category, urgency, attention, and Auditor fields never filter or rank retrieval. The result echoes `identity` as `KnowledgeResult.item_scope_ref`, and `item_id` joins the Knowledge contribution ID only for linked items.
- **Troubleshooting and Documentation** require the Knowledge echo to name the same item (`upstream_chain_mismatch`). Until `auditor_review` is `band_and_route_determined`, they return `blocked` with `missing_dependency` (Q-A: hold later processing).
- **Documentation** writes "Item n of m", shows the category as a Triage inference with its basis and sources, shows the Auditor's urgency band as an inference, and refers to an attention flag without repeating or clearing it. When the item has no flag, one Staff/Admin information line states the `attention_check` value. `check_not_run` adds no hold; the Auditor gates above still apply (S-1.1 Q3). It never shows another item's text.

**Not covered here (Manny's Lane, S-3 to S-8):** item-aware connector eligibility, source recheck, receipt identity, the linked-item bridge, attention scoping, and returning the item scope from `consume`.

## 4. Reason codes

Defined in `ReasonCode` (`contracts/common.py`). Main ones by gate:

- **Connection:** `context_mismatch`, `upstream_not_acknowledged`, `upstream_blocked`, `upstream_chain_mismatch`, `missing_dependency`.
- **A3 Knowledge:** `no_relevant_source`, `weak_evidence`, `stale_source_only`, `unapproved_source_only`, `conflicting_sources`, `multiple_approved_versions`, `retrieved_injection`. Per-source exclusions: `source_stale`, `source_not_effective`, `source_unapproved`, `source_retired`.
- **A4 Troubleshooting:** `knowledge_abstained`, `restricted_action_requested`, `unsupported_step_rejected`, `unknown_action_type`, `staff_only_procedure`, `policy_stop_condition`.
- **A6 Documentation:** `sensitive_data_detected`, `unsupported_claim`.

## 5. Open contract questions for Shared Lane / Manny's Lane

1. Does Triage produce `case_facts` with a per-field `verified` flag and `case_field` sources, as assumed here?
2. Is a coordinator-supplied acknowledged-ID set acceptable, or should acknowledgment be its own blackboard record type?
3. In the parallel pattern, Escalation runs before Troubleshooting. Should Escalation re-check after `escalation_signals` arrive, or should Documentation keep showing both (current behaviour)?
4. Should `TriageHandoff.product_area` use a controlled vocabulary shared with the knowledge metadata (`reports`, `access`, `login`, `documents`, `notifications`, `administration`)?
5. Who owns `RunContext.policy_version`: the coordinator's support policy, Triage, or both?
6. Is `0.1.0-proposed` → `0.1.0` the right promotion path once both lanes accept?
